# 服务广场接入标准治理规则

本规则落实 ADR 0005，适用于 `service-plaza.v1` 的内部板块和外部合作方接入。接入标准的业务 Owner 是平台集成负责人；APP 总架构负责人负责重大变更审批。

## 1. 角色与责任

| 事项 | 平台集成负责人 | APP 总架构负责人 | 板块负责人/合作方 | 安全与合规责任人 |
| --- | --- | --- | --- | --- |
| 标准、Schema、模板起草与维护 | A/R | C | C | C |
| 兼容性修订审批 | A/R | I | C | C |
| 新主版本或破坏性变更 | R | A | C | C |
| 服务广场信息架构、核心入口和统一认证边界 | R | A | C | C |
| 接入申请和清单准确性 | C | I | A/R | C |
| 本板块业务 API、数据、SLA 和运行支持 | C | I | A/R | C |
| Schema、路由、权限、返回路径和联调门禁 | A/R | I | R | C |
| 安全、隐私和监管专项验收 | C | I | R | A/R |
| 测试环境启用或停用 | A/R | I | R | C |
| 生产发布 | R | A | R | 按风险级别 A/R |

说明：A 为最终负责，R 为执行，C 为会签或咨询，I 为知会。同一事项的单个治理层只设置一个 A；表中安全与合规专项不转移板块/合作方的主体责任。

## 2. 平台集成负责人权限边界

平台集成负责人可以直接批准：

- 不改变既有字段含义的文字澄清和示例修正；
- 新增可选字段、可选能力或向后兼容的状态展示；
- Schema 校验、测试用例、模板和验收证据要求的兼容性增强；
- 单个服务按已发布标准接入、暂停、恢复或下线。

以下事项必须提交 APP 总架构负责人批准：

- 修改 `contract_version` 主版本或造成现有合规接入方不能继续工作的变更；
- 改变服务广场核心信息架构、核心服务范围、统一路由或返回路径规则；
- 改变认证交接方式、平台与板块的数据责任边界或隐私等级含义；
- 豁免 HTTPS、禁止 URL 传递凭据、权限预检等安全底线；
- 多方对变更级别存在争议，且平台集成负责人无法证明其向后兼容。

## 3. 接入方责任边界

板块负责人或外部合作方必须：

1. 指定业务、技术、安全/隐私和运行支持联系人。
2. 提交符合 Schema 的服务清单和真实可执行的测试证据。
3. 对业务 API、数据合法性、用户授权、服务可用性、错误处理和客户支持负责。
4. 在计划变更、停机、弃用或安全事件发生时按版本规则通知平台。
5. 不在 URL、日志、截图或 Handoff 中提交 JWT、验证码、手机号、健康信息或生产密钥。
6. 不直接修改服务广场结构、全局排序和统一认证规则。

平台验收只证明“可以按服务广场标准接入”，不证明接入方全部业务、医疗、支付或法律责任已经验收。

## 4. 标准治理流程

1. 提案人使用接入申请模板或变更提案说明需求。
2. 平台集成负责人判断是兼容修订、重大变更还是标准例外，并记录依据。
3. 兼容修订由平台集成负责人评审；重大变更由 APP 总架构负责人审批。
4. 先更新 ADR/标准/Schema/示例和契约测试，再允许接入实现依赖新规则。
5. 按版本策略发布并通知受影响方。
6. 通过接入验收清单和 Handoff 后，才可把服务状态改为 `active`。

## 5. 并行开发规则

- 已发布标准内的板块开发无需等待其他板块，可独立推进业务页面、API 和测试。
- 每个板块保留自己的业务仓库和验收责任，通过清单与 Handoff 在平台汇合。
- 一个板块的缺陷只阻止该板块进入 `active`，不得用降低全局标准的方式解除阻塞。
- 共享认证、目录接口、统一返回路径或 Schema 的缺陷属于平台阻塞，必须完成根因修复后再继续受影响接入。

## 6. 生效证据

一次接入只有同时具备以下记录才算完成治理闭环：

- 已签名或可追溯的接入申请；
- 通过 Schema 校验的服务清单；
- 完整验收清单及证据链接；
- 提交人与平台接收人确认的 Handoff；
- 版本、启用日期、回滚方法和运行联系人记录。

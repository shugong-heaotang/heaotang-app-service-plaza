# 服务广场接入标准版本兼容与弃用规则

## 1. 版本模型

服务清单中的 `contract_version` 表示协议主版本，第一版固定为 `service-plaza.v1`。标准发布记录使用 `主版本.次版本.修订版本`，例如 `1.2.1`。

- 主版本：不兼容变更，清单标识升级为 `service-plaza.v2`。
- 次版本：向后兼容地增加可选能力或规则。
- 修订版本：不改变字段语义的纠错、澄清、示例或测试修复。

同一个 Schema `$id` 对应的已发布内容必须保持不可变。需要改变 Schema 时发布新的可追溯版本，不得静默覆盖历史版本。

## 2. 变更分级

| 变更 | 级别 | 审批 |
| --- | --- | --- |
| 文字纠错、示例修正、校验器缺陷修复且不改变有效数据集合 | 修订版本 | 平台集成负责人 |
| 新增可选字段、可选枚举值、可选能力或兼容响应字段 | 次版本 | 平台集成负责人 |
| 删除/重命名字段、必填新增、类型改变、缩小有效值范围 | 主版本 | APP 总架构负责人 |
| 改变路由、认证、权限、隐私或返回路径语义 | 主版本 | APP 总架构负责人 |
| 安全漏洞紧急限制 | 紧急变更 | 平台集成负责人和安全负责人执行，APP 总架构负责人追认 |

无法证明向后兼容时，按主版本变更处理。

## 3. 兼容承诺

- 平台在同一主版本内接受此前符合该主版本的清单。
- 次版本新增字段默认可选；接入方不得因未知可选字段拒绝整个清单。
- 平台只依赖清单中已经发布的字段，不推断未声明的能力、权限或隐私等级。
- 接入方业务 API 版本独立于导航协议版本；任何一方升级都必须在清单中准确声明 `business_api_version`。
- 生产目录不得引用未发布、不可追溯或被原地覆盖的 Schema。

## 4. 弃用流程

1. 平台集成负责人建立弃用记录，列明范围、原因、替代方案、受影响服务和负责人。
2. 常规弃用至少提前 180 个自然日通知，并至少覆盖两个计划发布窗口。
3. 弃用期内旧主版本继续通过安全修复和必要运行支持，但不再增加新能力。
4. 平台逐一取得受影响接入方的迁移计划和测试证据。
5. 只有迁移验证、回滚方案和最终通知完成后，才能停止旧版本。
6. 下线后保留决策、通知、迁移和验收记录，不复用旧 `service_id`。

## 5. 紧急安全变更

存在已被利用的漏洞、凭据泄漏或法律禁止时，可以缩短通知期。平台集成负责人必须：

- 立即隔离受影响入口，状态改为 `maintenance` 或 `offline`；
- 记录风险、影响范围和临时保护措施；
- 取得安全负责人同意，并通知 APP 总架构负责人；
- 在恢复前完成根因修复、安全复测和接入方 Handoff；
- 不以“保持兼容”为理由继续暴露已知高风险行为。

## 6. 版本发布记录最小字段

每次发布至少记录：标准发布版本、协议主版本、发布日期、Owner、审批人、变更摘要、兼容性判断、受影响服务、迁移要求、弃用日期（如有）和证据链接。

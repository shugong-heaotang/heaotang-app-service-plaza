# 商城会员店方案吸收与 1.0 服务广场接入收口方案

更新时间：2026-07-12  
文档状态：商城侧正式建议稿，待平台集成负责人登记工作项并会签  
适用范围：保障商城、俱乐部商城、会员服务体验、Nova 协同、服务广场接入、商城 1.0 收口及 2.0—3.0 演进

## 一、决策摘要

“Nova 驱动的会员专属生活服务店”方案值得吸收，但不应整套替换现有商城，也不应在商城 1.0 上线收口阶段扩大功能范围。

最终采用以下产品与系统边界：

> 商城是平台统一的商品与服务交易履约底座；会员商城是面向会员的场景化服务体验；Nova 负责理解需求、解释选择、形成方案和推进服务，但不替代会员确认、商家履约、人工审核和专业人员判断。

执行结论：

1. 商城 1.0 保持交易、履约、售后、权益回滚和上线证据闭环，不引入复杂推荐与跨板块组合订单。
2. 服务广场只负责发现、展示、权限预检、安全导航、返回路径和入口遥测，不代理商城业务接口。
3. 保障商城与俱乐部商城继续作为两套业务规则存在；“会员商城”只作为统一体验层，不能成为第三套交易主体。
4. 原建议中的场景馆、会员决策页、我的服务中心、可解释推荐和 Nova 方案卡进入商城 2.0。
5. 跨模块方案、多商家子单、效果回流和受控复购进入商城 3.0。

## 二、原建议方案完整归纳

### 2.1 新定位

把会员店归入商城板块，并重新定义为 Nova 驱动的“会员专属生活服务店”。核心目标不是让会员浏览更多商品，而是帮助会员快速找到适合自己的商品、服务和解决方案，形成“咨询—推荐—下单—履约—评价—复购”闭环。

原建议采用“一店、两端、三个闭环”：

- 一店：会员看到统一的会员店。
- 两端：会员端与商家端。
- 三个闭环：需求闭环、交易闭环、关系闭环。

### 2.2 会员端页面

原建议将首页设计为五层：

1. “我的 Nova”需求入口：文字或语音表达问题，生成可执行会员方案卡。
2. “今日为我推荐”：少量高相关内容，必须说明推荐理由、依据、广告属性、价格、权益和履约主体。
3. 场景馆：健康与康养、家庭与养老、学习与成长、企业与商务、活动与社交、品质生活、会员专享、本地服务。
4. AI 方案店：多个商品、服务和权益组成可调整预算、可替换项目的解决方案。
5. 我的服务中心：把传统订单升级为方案、付款、预约、资料、履约、售后、效果跟踪与后续建议的持续服务过程。

### 2.3 Nova 在商城中的职责

原建议赋予 Nova 六项职责：

- 需求理解：整理对象、预算、地点、时间和目标。
- 个性化选品：在会员授权范围内筛选商品与服务。
- 方案组合：组合商品、服务、活动和权益。
- 购买解释：比较差异、价格、风险和推荐理由。
- 履约陪伴：提醒预约、材料、节点和售后。
- 复购运营：依据真实使用效果提出后续建议。

发布、报价承诺、交易、隐私披露、权益变更等关键动作必须由用户确认，AI 不得自主完成。

### 2.4 营销、语音和详情页

原建议主张营销从“卖流量”转向“卖结果”，考核需求匹配率、方案采纳率、履约完成率、退款投诉率、满意度、实际效果、复购率、响应速度和履约质量。广告必须明确标记，并与自然推荐分开。

语音遵循“轻声音、强语音、可关闭”，支持长按说需求、复述确认、语音对比、订单查询、大字版、慢速播报和字幕同步；公共场所默认只显示文字。

商品详情页从商品说明升级为会员决策页，展示解决的问题、适用和不适用人群、推荐理由、会员权益、履约标准、商家资质、售后规则、风险提示、替代方案及咨询入口。

## 三、吸收评审

### 3.1 直接吸收

#### 场景化前台

后台继续按商品类型、商家、库存、履约和结算管理；前台按会员生活场景聚合。会员无需先判断自己需要商品、课程、活动还是服务。

#### 会员决策页

详情页必须逐步补齐：解决的问题、适用边界、推荐理由、权益、履约责任、真实服务数据、退款售后、风险提示和替代方案。健康、养老和高客单服务优先展示边界、资质、流程和售后，不以促销信息为首要内容。

#### 我的服务中心

底层订单状态机保持稳定，会员侧增加“待预约、待提交资料、服务进行中、待核销、售后处理中、效果跟踪、下次建议”等服务视图。

#### 可解释推荐

所有 Nova 推荐必须说明推荐原因、使用的非敏感授权信息、广告属性、价格权益、履约主体、适用边界和关闭个性化推荐的方法。

#### 结构化方案卡

Nova 输出会员目标、服务对象、时间地点、预算、推荐组合、推荐理由、风险限制、替换项、预计价格和下一步行动。方案卡可以形成购物车或订单草稿，但必须逐项确认。

### 3.2 调整后吸收

#### “会员商城”是体验层，不是第三套商城

现有保障商城与俱乐部商城在准入、佣金、保障账户、经营范围和履约责任上不同，不能被统一名称掩盖。推荐前台结构为：

```text
商城
├─ 为我推荐
├─ 场景服务
├─ Nova 方案
├─ 保障商城
└─ 俱乐部商城
```

每个商品和方案必须明确所属商城、销售方、履约方、保障账户权益、分享大使收益与售后责任。

#### 首页采用双入口

Nova 需求入口服务于“不知道如何选”的会员；搜索、场景、订单、预约、复购和保障账户入口服务于目标明确的会员。AI 用于缩短路径，不强迫所有操作先对话。

#### 一个方案、多个子单

方案是聚合层，交易仍按商家、履约方式、结算规则和退款规则拆分子单。实物、服务、课程和活动不得被包装成无法独立履约和售后的单一订单。

### 3.3 不直接吸收

1. 不承诺普遍的服务结果。平台承诺推荐依据可解释、交易过程可追踪、履约标准可监督、投诉售后可处理，不承诺健康改善、学习成果或服务效果必然达成。
2. GraphRAG 不作为当前产品功能。先稳定会员授权、商品标签、服务条件、商家资质、订单结果、履约评价和售后数据，再决定技术实现。
3. 商家 AI 内容生成必须由商家确认；医疗、保险、养老等高风险内容需审核；不得生成无法证明的功效，不得利用隐私制造营销内容，不得让广告覆盖质量、相关性和信誉排序。

## 四、商城 1.0 固定范围

商城 1.0 继续以“可上线交易闭环版本”收口：

- 商品和服务浏览。
- 购物车、订单预览、下单及支付后状态。
- 实物物流与服务预约、核销。
- 售后、退款及权益回滚。
- 后台商品、订单、售后和关键操作。
- 权限、租户或俱乐部范围校验。
- 真实测试服 smoke、UAT、安全门、证据归档和 Go/No-Go。

1.0 不新增：

- 个性化推荐引擎。
- Nova 方案自动组合与跨模块任务执行。
- 多商家组合订单。
- GraphRAG。
- 自动营销和自动复购。
- 复杂促销、直播、拼团、砍价或多级分销。

## 五、服务广场标准化接入口

### 5.1 权威边界

服务广场采用 `service-plaza.v1` 导航接入协议和 `service-plaza.action.v1` 页面动作协议。服务广场负责：

- 服务发现、展示与排序。
- 生命周期与当前可用性表达。
- 登录与权限预检。
- 安全导航和统一返回路径。
- 入口点击遥测。

服务广场不代理商城内部业务 API。商城负责人对商品、订单、支付、退款、履约、售后和合规负责；平台集成负责人对导航协议、公共路由和接入门禁负责。

### 5.2 已预留入口

当前服务广场已预留：

| 字段 | 当前值 |
| --- | --- |
| action_id / service_id | `protection-mall` |
| 展示名称 | 保障商城 |
| 区域 | `common_services` |
| 排序 | 130 |
| 路由 | `/services/protection-mall` |
| 登录方式 | `shared_session` |
| 返回路径 | `/services` |
| 遥测事件 | `service_plaza.protection_mall.open` |
| 生命周期 | `planned` |

商城不得自行改变服务广场入口名称、位置、排序、底部导航或公共协议。商城侧交付完成并通过平台会签后，再由平台集成负责人把入口从 `planned` 推进到 `preview` 或 `active`。

### 5.3 商城应提交的接入卡

```text
板块名称：保障商城
负责人：商城板块负责人（待协作登记补齐）
入口显示名称：保障商城
所属层级：常用服务
一句话说明：面向会员的可信商品与生活服务交易履约平台
跳转目标页面：/services/protection-mall
返回页面：/services
是否需要登录：是，共享会话
是否需要会员权限：基础浏览按平台最终会签；下单、订单、账户和服务操作必须登录
是否涉及后台审核：是
是否涉及支付：是
是否涉及消息通知：是
业务接口版本：mall.api.v1（待平台会签）
需要的平台能力：共享会话、权限范围、统一 API 信封、request ID、幂等键、遥测、功能开关、支付安全、通知
空状态文案：暂时没有可购买的商品或服务
异常状态文案：商城服务暂时不可用，请稍后重试
验收负责人：商城负责人、平台集成负责人、APP 总架构负责人
```

## 六、商城接口调整方案

### 6.1 不改业务资源路径，补齐平台公共规范

商城现有 `/api/mall/*`、`/api/admin/mall/*`、`/api/assurance-mall/*` 和 `/api/clubs/{clubId}/mall/*` 资源边界总体可保留。1.0 收口重点不是重命名全部接口，而是补齐以下统一契约：

1. 明确 `mall.api.v1` 业务接口版本，并在文档、客户端和兼容性门禁中统一。
2. 统一成功与错误信封，禁止接口各自返回不同结构。
3. 每个请求和响应携带或回传 request/correlation ID，贯通服务广场入口、商城前端、商城 API、支付与履约日志。
4. 创建订单、支付回调、退款、核销、权益回滚、提现和关键审核必须使用幂等键或等效原子约束。
5. 统一权限 scope，不只使用“登录会员/平台运营”等文字描述；具体 scope 需由平台集成负责人会签。
6. 关键配置失败关闭，佣金、比例、保证金、有效期、退款窗口等不得依赖前端硬编码默认值。
7. 写操作留下审计事件，AI 建议与人工决定分别记录。
8. 增加接口版本差异门禁；破坏性变更必须升级版本，不能静默替换字段。

### 6.2 建议的最小入口接口

为 `/services/protection-mall` 提供最小可联调读接口，避免服务广场直接拼装商城业务数据：

| 接口 | 用途 | 1.0 要求 |
| --- | --- | --- |
| `GET /api/mall/entry` | 返回商城入口状态、可见范围、基础导航和业务接口版本 | 必须 |
| `GET /api/mall/products` | 商品与服务列表 | 已有，需统一信封/分页/版本 |
| `GET /api/mall/products/{productId}` | 商品或服务详情 | 已有，需补责任方与履约字段 |
| `GET /api/mall/me/permissions` | 当前会员可用动作 | 已有，需与 scope 会签 |
| `GET /api/mall/orders` | 我的订单 | 已有，需覆盖空、异常和越权 |

`GET /api/mall/entry` 建议返回：

```json
{
  "contract_version": "mall.api.v1",
  "service_id": "protection-mall",
  "lifecycle_status": "preview",
  "available": true,
  "return_target": "/services",
  "capabilities": ["browse", "order", "fulfillment", "after_sale"],
  "request_id": "<server-generated-id>"
}
```

其中 `lifecycle_status` 和 `available` 必须由环境、功能开关和依赖门禁计算，不得由前端假定。

### 6.3 商品详情需补齐的责任字段

1.0 接入服务广场前，商品详情 DTO 至少明确：

- `mall_type`：保障商城或俱乐部商城。
- `merchant_id`、`merchant_display_name`：销售责任主体。
- `fulfillment_provider`：履约责任主体。
- `product_type`：实物或服务。
- `fulfillment_mode`：物流、预约核销或其他受控类型。
- `after_sale_policy`：售后规则引用及摘要。
- `risk_disclosures`：风险和边界提示。
- `assurance_benefit_eligible`：是否产生保障账户权益。
- `promotion_disclosure`：是否广告或付费推广。

2.0 再增加推荐理由、适用/不适用人群、替代方案和 Nova 方案引用，避免把 2.0 字段强行塞进 1.0 收口。

## 七、1.0 收口门禁

商城从服务广场 `planned` 推进到 `preview` 前必须满足：

1. 平台集成负责人下达商城工作项，明确专用 `codex/` 分支、工作树、基线和允许路径。
2. 商城依赖门禁达到 development Go，完成当前起飞检查单与 100 分治理考试。
3. 商城接入清单通过 `service-plaza.v1` Schema 与版本兼容性检查。
4. `/services/protection-mall` 路由可访问，未登录、无权限、维护中、空数据和异常状态处理正确，返回 `/services` 正常。
5. `mall.api.v1` 的信封、request ID、权限、幂等、审计和兼容性门禁通过。
6. 商品—订单—支付状态—履约—售后—退款—权益回滚主链路通过真实测试服验收。
7. 支付安全、资金状态机、回调验签、退款与对账取得独立验收；未通过时不得从 `preview` 转 `active`。
8. 形成 implementation record、Handoff、测试证据、编码检查、安全检查、回滚方案和 Go/No-Go 结论。

## 八、实施顺序

### 检查点 M0：正式授权和契约冻结

- 登记商城工作项、负责人、工作树、分支、基线和允许路径。
- 确认 `mall.api.v1`、入口路由、权限 scope 和接入卡。
- 将本文件迁入官方项目仓库并会签。

### 检查点 M1：服务广场入口适配

- 提交 `service-plaza.v1` 商城清单。
- 实现 `/services/protection-mall` 最小入口页和返回路径。
- 实现或适配 `GET /api/mall/entry`。
- 打通入口遥测和 request ID。

### 检查点 M2：商城 1.0 交易履约接口收口

- 统一 API 信封、分页、错误码和版本声明。
- 完成权限、幂等、审计、关键配置失败关闭。
- 验证实物与服务两类履约及售后回滚。

### 检查点 M3：真实环境验收

- 先只读预检，再执行经授权的写入验证。
- 完成公开入口、深链接、静态资源、API ready、登录、订单、履约、售后和权限隔离证据。
- 完成归档完整性检查和 Go/No-Go。

### 检查点 M4：商城 2.0 产品体验

- 场景馆。
- 会员决策页。
- 我的服务中心。
- 可解释推荐字段。
- Nova 需求入口与结构化方案卡。

### 检查点 M5：商城 3.0 智能协同

- 一个方案、多商家子单。
- 跨模块任务编排。
- 履约效果回流。
- 受控复购和主动提醒。
- 在数据稳定后评估关系网络或 GraphRAG。

## 九、当前事实与阻塞

截至 2026-07-12：

- 本地商城工作区已有 1.0 原型、接口草案、验证脚本和 WP3 收口材料，但存在大量未提交的历史修改，不能整体暂存或覆盖。
- 当前商城本地仓库与正式服务广场仓库边界不同，不能把本地历史强推到官方仓库。
- 服务广场协作登记中没有商城专用活动工作项、专用工作树、分支和允许路径。
- 服务广场的 `contracts/service-plaza`、`docs/decisions` 和脚本属于受保护路径，商城侧不能自行修改。
- 因此当前可完成商城侧方案、差距分析和接入申请；正式接口代码、服务广场生命周期状态变更及 GitHub 官方留存必须在平台集成负责人登记 M0 后执行。

## 十、最终产品表述

不采用“平台对所有服务结果负责”的过度承诺，统一表述为：

> 传统商城帮助会员找到商品；会员商城帮助会员形成解决方案，并让推荐依据、交易过程和服务履约全程可追踪。

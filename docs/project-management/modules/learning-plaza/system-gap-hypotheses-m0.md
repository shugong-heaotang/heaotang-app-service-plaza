# 学习广场启动后暴露的体系缺口（M0 假设）

这些是通过学习广场核心合同化已经能够证明或需要在 M1-M3 验证的体系问题，不是最终综合验收结论。

1. **项目归属倒置**：Nova 仓库已有可运行学习广场，但 v3.0 已确认 Nova 学习助手只是学习广场内部应用、Nova AI Engine 才是共享能力。现有运行时不能原样迁入，必须先拆分宿主与引擎边界。
2. **资源统一身份缺失**：文章、课程、书籍、笔记、直播和回放尚无平台统一资源 ID、版本和来源模型，跨路径引用容易形成重复或失效对象。
3. **内容版权与责任主体未冻结**：现有计划强调内容，但没有形成可执行的授权来源、许可范围、下架、留存与审计合同。
4. **跨模块数据所有权模糊**：生命导航推荐、俱乐部会员、学习进度、Nova 引用和成长回写若直接共享表，会造成循环依赖和越权写入。
5. **成长回写缺少事件标准**：课程/读书/共学完成如何更新生命导航尚无统一幂等事件、消费者确认和重放语义。
6. **可见性不能只靠前端**：公开、登录、俱乐部和私有内容需要服务端 owner/scope 双校验；现有静态参考页面不能证明该边界。
7. **AI 引用与代执行边界需平台化**：Nova 必须仅检索用户可见资源、返回引用并禁止代用户完成、发布、入会、消息和购买；这不能由单个页面提示保证。
8. **学习状态机与幂等尚未进入共享能力**：接受路径、推进、放弃、恢复、完成与重复提交需要稳定机器码和幂等冲突语义。
9. **模块生命周期门禁不完整**：服务目录的 `planned/preview/active` 与模块 readiness、独立验收、部署状态之间尚未自动联动。
10. **审核开关缺少运行时治理**：AI 与人工审核可独立开关，但开关必须进入版本化双人审批；双关仍需授权发布与完整审计，不能解释为无治理。
11. **独立验收是实际吞吐瓶颈**：开发可快速并行，但 reviewer/owner 确认、跨模块契约签署和受控集成仍决定真实完成速度。

建议验证顺序：先验收独立项目骨架和运行时归属，再统一资源身份与版权责任、冻结五个连接端口，随后实现课程闭环，最后做成长投影、Nova 引用与知识商品验收。

## 1. 文档目的

本 PRD 把健康大管家的长期产品宪法压缩为一个可评审、可测试、可继续拆分的 90 天最小产品，同时保留会员需求汇总形成长期业务的资源地图。

本阶段不是建设完整健康生态，也不是把全部会员需求都变成首期功能。MVP-90 只验证：

1. 会员是否能理解自己的健康关注点；
2. 是否能形成一份本人确认、管理师审核的健康计划；
3. 是否能持续完成和反馈每日行动；
4. 是否能完成至少一次 PDCAR；
5. 风险、授权、资料不足和 AI 故障是否能够安全转人工；
6. 会员是否愿意继续使用并接受后续付费服务假设。

## 2. 权威边界

### 2.1 本 PRD 可以确定

- 8 个会员逻辑页面和 5 个管理逻辑页面；
- 最小 PDCAR 流程、对象和可观察状态；
- AI、健康管理师、医生、会员和平台的职责边界草案；
- 合成数据验收和 Day 0/1/7/30/90 成功证据；
- 52 项长期会员需求业务地图及其 MVP 范围分类；
- 后续业务切片和外部合作能力的规划方式。

### 2.2 本 PRD不能自行确定

- 医疗责任主体、诊疗边界和疾病疗效承诺；
- 风险分级规则、紧急值班和无法联系机制；
- 健康管理师准入、培训、标准工时、容量和响应承诺；
- 健康数据保留、导出、删除、未成年人和特殊人群规则；
- 具体价格、套餐金额、积分价值、分润和资金结算；
- 真实会员试运行、生产、部署和真实健康数据使用。

以上事项必须保持 `Pending with owner`，不得由 AI 或模块负责人单方改为 Accepted。

## 3. 首批会员与核心问题

### 3.1 建议首批会员

产品建议以“能够本人授权、愿意完成基本测评、希望改善生活方式并接受管理师协同的成年会员”为首批对象。

慢病用药、近期明显不适、老年跌倒高风险、孕产、未成年人、认知能力受限以及需要诊疗判断的人群，不在普通自动化路径中直接形成确定性建议；只能在获得专业规则后进入人工或专业协同。

首批会员的正式纳入和排除条件仍为 `Pending`，责任人为产品负责人和和奥堂医生集团专业负责人。

### 3.2 首要问题

会员通常不是缺少一篇健康知识，而是：

- 不知道自己最需要关注什么；
- 体检、日常行为和医生建议相互分散；
- 没有年度目标和每天可执行的行动；
- 做了以后没人检查、调整和长期记录；
- 出现风险时不知道应该找谁；
- 不知道哪些建议来自 AI、管理师或医生。

### 3.3 MVP-90 的承诺

- 帮助会员整理资料和需求；
- 形成可解释的健康计划草案；
- 把计划拆成可执行任务；
- 记录完成、困难、不适和变化；
- 通过管理师审核和周期复盘持续调整；
- 在出现规则风险、资料不足或能力边界时转人工；
- 保留来源、版本、时间和责任人记录。

### 3.4 禁止承诺

- 不承诺诊断、处方、改药、治愈或延长寿命；
- 不承诺避免所有疾病、跌倒或紧急事件；
- 不把完成任务等同于医疗效果；
- 不用“健康年龄”“抗摔”等营销表达暗示确定性保证；
- 不因销售、积分或合作单位利益改变专业建议；
- 不在授权和专业规则缺失时使用宽松默认值继续服务。

## 6. 最小 PDCAR 覆盖

| 环节 | 会员语言 | MVP 页面 | 最低结果 |
|---|---|---|---|
| P — Plan | 我想改善什么，准备怎么做 | 测评、计划、计划审核 | 已审核且会员确认的计划版本 |
| D — Do | 我今天做什么 | 首页、今日任务、AI | 一个首要行动及执行反馈 |
| C — Check | 我做得怎么样，出现了什么变化 | 今日任务、会员与风险 | 完成、困难、不适和风险记录 |
| A — Advance | 下一步怎样调整 | 计划审核、联系管理师 | 有依据的调整草案和新版本确认 |
| R — Record | 我的变化有没有留下记录 | 档案、沟通与服务记录、我的 | 来源、时间、责任人和版本可追溯 |

任一环节缺失，不能把产品宣称为完整最小健康管理闭环。

## 7. 会员需求业务形成机制

健康大管家面对会员提供统一入口，和奥堂医生集团作为健康管理总包组织内部和外部能力。会员不需要自行在大量机构之间反复解释和判断。

```text
会员提出需求
→ AI和管理师识别、分类
→ 相同需求进入会员健康需求池
→ 判断内部服务、专业转介或外部采购
→ 形成标准服务包
→ 匹配经审核的合作单位
→ 服务交付与结果回传
→ 质量、风险和满意度复盘
→ 保留、整改、替换或退出供应商
```

所有服务统一遵守：真实需求、适用性评估、本人授权、资质核验、方案明确、价格透明、过程留痕、结果结构化、风险升级、质量评价、最小数据使用和可退出。

## 13. C2 PDCAR 主流程

### 13.1 主链路

```text
会员进入并阅读边界
→ 确认本人身份与最小授权
→ 完成安全筛查、需求访谈与渐进建档
→ AI 形成带来源和不确定性说明的计划草案
→ 管理师审核；必要时补资料或转专业人员
→ 会员确认计划版本
→ 生成一个今日首要行动
→ 会员完成、部分完成、延后、无法完成或因不适暂停
→ 系统和管理师检查执行、困难、变化与风险
→ 形成调整草案，审核并由会员确认新版本
→ 将计划、执行、检查、调整和责任记录写入成长档案
```

以下分流优先于普通主链路：

- 紧急规则命中：立即中止普通计划生成，显示紧急引导并创建人工处置事件；
- 资料不足：只进入待补资料或人工澄清，不形成确定性结论；
- 专业判断需要：只建立最小转介包，未经授权不开放完整档案；
- 会员撤回授权：立即停止新的非必要处理，历史记录按正式保留规则处置；
- AI、人员、规则、模板或关键配置不可用：失败关闭并提供人工或稍后恢复路径。

### 13.2 PDCAR 完整性不变量

| 环节 | 必须存在的对象 | 必须留下的证据 | 禁止替代 |
|---|---|---|---|
| P | 目标、计划、计划版本 | 来源、审核人、会员确认和生效时间 | AI 草案不能冒充生效计划 |
| D | 任务、执行反馈 | 行动内容、计划来源、反馈时间和会员选择 | 提醒发送不能冒充会员执行 |
| C | 检查记录、风险事件 | 观察、偏差、不适、规则版本和责任人 | 打卡次数不能冒充健康效果 |
| A | 调整草案、新计划版本 | 调整依据、审核、差异和会员确认 | 静默覆盖旧计划或专业意见 |
| R | 成长档案、服务记录、审计事件 | 来源、时间、角色、版本和更正链 | 删除或改写历史记录掩盖变化 |

任一环节缺少上述最低证据时，页面必须显示“闭环未完成”及下一步，不得以汇总分数或营销文案掩盖缺口。

## 14. C2 核心对象与最低字段

本节定义产品对象，不定义数据库 Schema 或接口字段。字段名称是 PRD 语义名，后续接口工作项必须另行评审。

| 对象 | 最低语义字段 | 创建/确认责任 | 关键约束 |
|---|---|---|---|
| `MemberServiceRelationship` 会员服务关系 | 会员、责任管理师、服务状态、开始/结束、适用产品 | 平台建立，运营受控确认 | 没有有效关系不能访问管理视图；到期不自动删除档案或关闭风险 |
| `ConsentGrant` 授权 | 授权主体、目的、数据范围、接收角色、有效期、状态、版本 | 会员确认 | 目的和范围分离；撤回阻止新的非必要访问 |
| `HealthProfileItem` 健康档案项 | 内容、类型、来源、发生/采集时间、确认状态、更正链 | 会员、管理师或专业人员按来源确认 | 候选信息不得静默变成已确认事实 |
| `AssessmentSession` 测评会话 | 适用规则、问题版本、回答、缺失项、安全筛查结果、分流 | 会员作答，系统分流，人工复核 | 不输出诊断；资料不足必须显式存在 |
| `HealthGoal` 健康目标 | 目标描述、优先级、周期、成功观察方式、状态 | 会员确认，管理师协助 | 不能只以购买、打卡或单一数值定义成功 |
| `HealthPlan` 健康计划 | 当前版本、目标、适用周期、责任关系、状态 | 管理师审核、会员确认 | 只指向一个当前生效版本；历史版本不可覆盖 |
| `HealthPlanVersion` 计划版本 | 版本号、草案来源、行动、检查、停止条件、调整依据、审核与确认 | AI 可起草；管理师/专业人员审核；会员确认 | 专业内容必须保留签署来源；未经确认不得生效 |
| `HealthTask` 健康任务 | 来源计划版本、行动、计划日期、停止条件、状态 | 系统按已生效计划生成 | 不得脱离计划来源；一个首要行动优先 |
| `TaskFeedback` 任务反馈 | 会员选择、困难、不适、备注、时间、来源 | 会员提交 | 原始反馈保留；AI 摘要不能覆盖原文 |
| `CheckRecord` 检查记录 | 检查对象、观察、偏差、资料来源、结论类型、责任人 | 系统整理，管理师复核 | 检查不等同诊断或疗效判断 |
| `RiskEvent` 风险事件 | 来源、原始描述、规则版本、暂定级别、状态、责任人、措施、复核 | 系统/人员创建，合格人员处置 | AI 不得独立关闭专业或紧急事件 |
| `HumanHandoff` 转人工事件 | 触发原因、最小上下文、目标角色、队列状态、接管人、结果、恢复点 | 系统触发或会员/人员发起 | 发送成功不等于已接管；必须可追踪无法联系 |
| `CommunicationRecord` 沟通记录 | 参与角色、渠道、发送/送达/回复状态、内容来源、下一步 | 人工沟通为主，AI 可整理 | 已发送、已送达、已解决三种事实不得混同 |
| `ServiceRecord` 服务记录 | 服务类型、执行主体、时间、过程、结果、异常、后续 | 实际服务责任方 | 订单或核销状态不能冒充专业结果 |
| `TemplateVersion` 模板版本 | 模板类型、适用范围、禁忌、审核状态、版本、有效期 | 内容维护者录入、独立审核人批准 | 同人审核拒绝；未审核或过期模板不可生成计划 |
| `AuditEvent` 审计事件 | 操作者、角色、动作、对象、时间、结果、原因、关联 ID | 平台自动记录 | 不记录健康正文、密钥或不必要个人信息 |

## 15. C2 核心状态机

### 15.1 开始健康管理

```text
未开始
→ 已阅读服务边界
→ 待最小授权
→ 安全筛查中
→ 可继续 / 待补资料 / 转人工 / 紧急引导 / 已停止
```

- `紧急引导` 不得直接回到普通计划生成；只有合格人工角色记录处置结果并明确恢复条件后才可重新评估。
- `待补资料` 不能自动超时变成“无风险”或“可继续”。

### 15.2 健康计划及版本

```text
AI草案
→ 待管理师审核
→ 待补资料 / 待专业审核 / 待会员确认
→ 已生效
→ 已暂停 / 已恢复 / 被新版本替代 / 已结束
```

- 管理师退回草案必须说明原因；AI 重新生成时保留前版和差异。
- 专业意见被新版本引用时必须保留原始来源、适用范围和签署时间。
- 会员拒绝确认时保持未生效，不以默认同意或持续使用推断同意。

### 15.3 健康任务

```text
待开始
→ 进行中
→ 完成 / 部分完成 / 延后 / 无法完成 / 因不适暂停 / 已取消
→ 待检查
→ 已记录 / 转人工
```

- `因不适暂停` 立即阻止继续鼓励该任务，并按已审核规则转人工。
- `延后`、`无法完成` 和过期不等于会员失败，不自动扣减健康信用或权益。

### 15.4 风险事件

```text
已发现
→ 待初步分级
→ 提醒 / 关注 / 专业 / 紧急
→ 待接管 / 处理中 / 无法联系
→ 待复核
→ 继续观察 / 升级 / 人工关闭
```

- 四级名称只表达工作流类别，具体判定规则、响应时限和值班责任继续 `Pending with owner`。
- AI 可以识别规则触发、保存原始描述和发起转人工，但不能独立降低级别或关闭专业、紧急事件。
- 无法联系必须保留尝试、渠道、时间和下一步，不得写成已解决。

### 15.5 转人工与沟通

```text
已触发
→ 待路由
→ 待接管
→ 已接管
→ 待会员 / 待专业 / 处理中 / 无法联系
→ 待复核
→ 恢复普通流程 / 升级 / 人工关闭
```

- 路由到队列、消息发送和人员打开页面都不等于接管；只有具备资格且未超容量的责任人显式接受后才进入 `已接管`。
- 关闭必须包含处理结果、责任人、依据和后续动作；需要诊疗判断时只能由相应专业角色关闭专业部分。

### 15.6 授权

```text
草稿
→ 待确认
→ 生效 / 部分授权 / 拒绝
→ 变更 / 撤回 / 到期 / 服务结束
```

- 变更生成新版本，不覆盖历史同意内容。
- 撤回后，所有新的非必要读取、AI 处理、共享和外部转介失败关闭；历史记录的保留、导出和删除规则继续 Pending。

## 18. C2 转人工、接管与恢复规则

### 18.1 必须触发转人工

- 会员主动请求人工或对 AI 输出提出异议；
- 本人身份、服务关系或必要授权无法确认；
- 安全筛查资料不足而影响继续判断；
- 会员报告不适、明显变化或规则红旗；
- AI 输出与已签署专业意见、已生效计划或会员原始资料冲突；
- 涉及诊断、处方、改药、治疗饮食、专业康复或其他资质限定动作；
- 风险规则、模板、人员资格、责任人或关键配置缺失、失效；
- 管理师超过安全容量或当前责任人不可用；
- 外部服务结果缺少来源、签署、时间或适用范围；
- 重复写入风险、计划或服务记录的幂等依据不足。

### 18.2 最小转介包

转人工默认只包含：触发原因、会员当前问题原文、相关对象 ID、必要摘要、来源与时间、当前授权范围、已经采取的安全动作。不得默认附加完整档案、无关历史、营销画像或家庭成员资料。

### 18.3 接管资格

接管前平台必须验证：有效身份、有效服务关系、角色权限、专业资质或服务授权、当前容量、利益冲突与必要数据授权。任一必需条件不可验证时保持 `待接管` 或升级，不使用宽松默认值。

### 18.4 恢复普通流程

只有人工处理结果同时明确以下内容后，普通流程才能恢复：

1. 哪个风险或边界已处理、仍有哪些未知；
2. 谁在什么资格和范围内作出判断；
3. 允许恢复的计划、任务或页面范围；
4. 新的停止条件、复核要求和责任人；
5. 会员是否需要重新确认计划或授权。

恢复不删除风险、转人工或旧计划记录；系统创建新版本并保留关联链。

### 18.5 AI 故障与人工替代

- AI 不可用时，会员仍可查看已确认计划、提交任务反馈、查看紧急入口和联系管理师；
- AI 生成超时、失败或内容被安全拦截时，不产生半生效计划或任务；
- 人工可以基于已授权资料继续处理，但不得把 AI 故障作为扩大数据访问的理由；
- AI 恢复后只能重新生成草案，不得覆盖故障期间人工签署的记录。

## 19. C2 失败关闭清单

以下条件必须阻止相应动作，并形成稳定、可观察的失败原因；错误标识和接口表达留待后续独立契约工作项：

1. 无有效本人身份或服务关系时读取管理数据；
2. 必需授权缺失、过期或撤回后继续 AI 处理或共享；
3. 资料不足时生成确定性报告或生效计划；
4. 未审核、已过期或不适用模板生成任务；
5. 未经会员确认使计划生效；
6. AI 或管理师尝试修改诊疗、处方或用药意见；
7. AI 尝试降低或关闭专业、紧急风险；
8. 无合格且未超容量人员时宣称已接管；
9. 消息已发送、订单已完成或服务已核销时推断专业问题已解决；
10. 关键规则、资质、责任人、配置或幂等依据缺失时继续写入。

## 21. C2 检查点验收标准

C2 只有同时满足以下条件才可提交平台复核：

- 主流程覆盖 P、D、C、A、R，并列明紧急、资料不足、专业、撤权和故障分流；
- 16 个核心产品对象都有最低语义字段、责任和安全约束，但没有越权定义 Schema；
- 六组状态机区分发送、接管、处理、复核和关闭，不把中间状态冒充结果；
- 8 个会员页面和 5 个管理页面能追踪到对象、动作及边界；
- AI、管理师、医生/专业人员、医生集团和平台责任不相互冒充；
- 转人工触发、最小转介包、接管资格、恢复和 AI 故障替代均可测试；
- 医疗、隐私、价格、容量、时限和试运行事项继续为 `Pending with owner`；
- 没有新增业务代码、接口、Schema、环境、部署、生产或真实数据。

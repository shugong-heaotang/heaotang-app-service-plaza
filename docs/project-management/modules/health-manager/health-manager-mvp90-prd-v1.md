## 1. 文档目的

本 PRD 把健康大管家的长期产品宪法压缩为一个可评审、可测试、可继续拆分的 90 天最小产品，同时保留会员需求汇总形成长期业务的资源地图。

本阶段不是建设完整健康生态，也不是把全部会员需求都变成首期功能。MVP-90 只验证：

1. 会员是否能理解自己的健康关注点；
2. 是否能形成一份本人确认、管理师审核的健康计划；
3. 是否能持续完成和反馈每日行动；
4. 是否能完成至少一次 PDCAR；
5. 风险、授权、资料不足和 AI 故障是否能够安全转人工；
6. 会员是否愿意继续使用并接受后续付费服务假设。

## 2. 权威边界

### 2.1 本 PRD 可以确定

- 8 个会员逻辑页面和 5 个管理逻辑页面；
- 最小 PDCAR 流程、对象和可观察状态；
- AI、健康管理师、医生、会员和平台的职责边界草案；
- 合成数据验收和 Day 0/1/7/30/90 成功证据；
- 52 项长期会员需求业务地图及其 MVP 范围分类；
- 后续业务切片和外部合作能力的规划方式。

### 2.2 本 PRD不能自行确定

- 医疗责任主体、诊疗边界和疾病疗效承诺；
- 风险分级规则、紧急值班和无法联系机制；
- 健康管理师准入、培训、标准工时、容量和响应承诺；
- 健康数据保留、导出、删除、未成年人和特殊人群规则；
- 具体价格、套餐金额、积分价值、分润和资金结算；
- 真实会员试运行、生产、部署和真实健康数据使用。

以上事项必须保持 `Pending with owner`，不得由 AI 或模块负责人单方改为 Accepted。

## 3. 首批会员与核心问题

### 3.1 建议首批会员

产品建议以“能够本人授权、愿意完成基本测评、希望改善生活方式并接受管理师协同的成年会员”为首批对象。

慢病用药、近期明显不适、老年跌倒高风险、孕产、未成年人、认知能力受限以及需要诊疗判断的人群，不在普通自动化路径中直接形成确定性建议；只能在获得专业规则后进入人工或专业协同。

首批会员的正式纳入和排除条件仍为 `Pending`，责任人为产品负责人和和奥堂医生集团专业负责人。

### 3.2 首要问题

会员通常不是缺少一篇健康知识，而是：

- 不知道自己最需要关注什么；
- 体检、日常行为和医生建议相互分散；
- 没有年度目标和每天可执行的行动；
- 做了以后没人检查、调整和长期记录；
- 出现风险时不知道应该找谁；
- 不知道哪些建议来自 AI、管理师或医生。

### 3.3 MVP-90 的承诺

- 帮助会员整理资料和需求；
- 形成可解释的健康计划草案；
- 把计划拆成可执行任务；
- 记录完成、困难、不适和变化；
- 通过管理师审核和周期复盘持续调整；
- 在出现规则风险、资料不足或能力边界时转人工；
- 保留来源、版本、时间和责任人记录。

### 3.4 禁止承诺

- 不承诺诊断、处方、改药、治愈或延长寿命；
- 不承诺避免所有疾病、跌倒或紧急事件；
- 不把完成任务等同于医疗效果；
- 不用“健康年龄”“抗摔”等营销表达暗示确定性保证；
- 不因销售、积分或合作单位利益改变专业建议；
- 不在授权和专业规则缺失时使用宽松默认值继续服务。

## 6. 最小 PDCAR 覆盖

| 环节 | 会员语言 | MVP 页面 | 最低结果 |
|---|---|---|---|
| P — Plan | 我想改善什么，准备怎么做 | 测评、计划、计划审核 | 已审核且会员确认的计划版本 |
| D — Do | 我今天做什么 | 首页、今日任务、AI | 一个首要行动及执行反馈 |
| C — Check | 我做得怎么样，出现了什么变化 | 今日任务、会员与风险 | 完成、困难、不适和风险记录 |
| A — Advance | 下一步怎样调整 | 计划审核、联系管理师 | 有依据的调整草案和新版本确认 |
| R — Record | 我的变化有没有留下记录 | 档案、沟通与服务记录、我的 | 来源、时间、责任人和版本可追溯 |

任一环节缺失，不能把产品宣称为完整最小健康管理闭环。

## 7. 会员需求业务形成机制

健康大管家面对会员提供统一入口，和奥堂医生集团作为健康管理总包组织内部和外部能力。会员不需要自行在大量机构之间反复解释和判断。

```text
会员提出需求
→ AI和管理师识别、分类
→ 相同需求进入会员健康需求池
→ 判断内部服务、专业转介或外部采购
→ 形成标准服务包
→ 匹配经审核的合作单位
→ 服务交付与结果回传
→ 质量、风险和满意度复盘
→ 保留、整改、替换或退出供应商
```

所有服务统一遵守：真实需求、适用性评估、本人授权、资质核验、方案明确、价格透明、过程留痕、结果结构化、风险升级、质量评价、最小数据使用和可退出。

## 9. 老年会员跌倒预防专项

### 9.1 需求结论

原 52 项地图只在 B45 中概括“跌倒风险”，不足以指导开发和外部合作。正式表达应为“老年跌倒风险预防与跌倒后处置”，不能用“抗摔”暗示保证会员不会跌倒或受伤。

### 9.2 专项服务链

| 子业务 | 服务内容 | 最低标准 | MVP-90 |
|---|---|---|---|
| B45-F1 跌倒风险筛查 | 既往跌倒、步态、平衡、肌力、视力、用药、认知和环境风险 | 规则来源、适用人群、资料不足和红旗转介明确 | 只做经专业审核后的最小入口；当前 Pending |
| B45-F2 家庭环境评估 | 地面、照明、扶手、浴室、床椅、楼梯和鞋具 | 现场或受控远程评估，整改前后有记录 | 后置 |
| B45-F3 肌力和平衡训练 | 下肢力量、平衡和安全活动训练 | 运动风险筛查、停止条件、专业指导和阶段复评 | 后置 |
| B45-F4 视力、用药和设备复核 | 识别影响跌倒的视力、药物和辅具问题 | 药物由医生或药师判断，设备合法并正确适配 | 后置 |
| B45-F5 紧急与跌倒后处置 | SOS、联系人、是否送医、跌倒原因复盘和计划调整 | 不移动疑似严重损伤会员，按急救规则升级 | 后置；MVP只保留紧急入口 |
| B45-F6 家属和照护者培训 | 安全陪护、环境维护、异常识别和沟通 | 不替代专业服务，培训内容审核并留痕 | 后置 |

### 9.3 当前开发覆盖判断

- 已在 MVP 范围中存在：健康测评、资料不足分流、风险转人工、今日任务“不适暂停”、管理师接管和紧急入口。
- 尚未形成：跌倒风险专业规则、老年专项字段、家庭环境评估、肌力平衡计划、药师复核、辅具适配、紧急服务 SLA、跌倒后随访状态机。
- 因此当前不能声称“养老抗跌倒功能已经完成”，只能说“具备承载该需求的风险筛查和转人工框架”。
- 如果平台后续批准业务实现，建议在 MVP 基础切片之后单独建立 `HM-ELDER-FALL-PREVENTION` 专项 PRD 和工作项。

## 11. 业务点的统一服务标准

每项服务必须形成：

1. 明确的会员需求和适用条件；
2. 本人授权及最小数据范围；
3. 服务主体、专业人员和资质；
4. 目标、周期、频率、责任人和退出条件；
5. 价格类型和退款规则；具体金额不得在 PRD 中硬编码；
6. 预约、执行、结果回传和异常状态；
7. 结构化交付物及来源、时间和版本；
8. 红旗风险、暂停、人工升级和无法联系规则；
9. 完成度、及时性、投诉、异常和质量评价；
10. 资质失效、重大投诉或连续不合格后的暂停与退出。

合作单位状态建议为：

```text
候选 → 资质审核 → 试服务 → 正式入库 → 周期考核
    → 暂停整改 → 恢复或退出
```

正式时限、价格、容量和质量阈值全部保持 Pending，并由版本化配置及 maker-checker 流程管理。

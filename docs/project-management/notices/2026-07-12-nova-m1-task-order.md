## 一、项目裁决

NOVA 采用“底座提前开发、业务能力随板块逐步接入、APP 上线前完成综合智能化验收”的路线。

人脉和活动可以排在 NOVA 业务闭环之前，但不得排在 NOVA 基础设施、工具接口、权限、确认和事件规范之前。上线前阶段用于真实数据联调、UAT、安全和收口，不得成为 NOVA 核心能力首次开发阶段。

## 二、本任务目标

平台集成负责人牵头启动 NOVA 第五阶段 M1，先形成可被人脉、活动和消息等板块共同遵守的任务运行底座与接口契约：

1. `/api/nova/chat` 统一入口的版本化契约。
2. 任务、步骤、事件、人工确认和恢复状态机。
3. 工具注册、调用、审批、结果回传和失败分类协议。
4. 租户、身份、权限、数据授权、审计和幂等边界。
5. 模型路由、额度和成本记录边界。
6. 人脉与活动工具的 mock 契约及兼容性测试夹具。
7. 后续“找人闭环”和“活动闭环”的接入检查点与 Handoff 入口。

本阶段允许使用 mock 数据和模拟工具验证协议，不等待人脉或活动全部页面完成。

## 五、后续阶段门禁

### M1：运行时与公共契约

交付统一入口、状态机、工具网关、权限/租户/审计/幂等、成本记录以及 mock 工具契约。阶段成果必须可单独测试和恢复。

### M2：人脉真实闭环

在人脉接口达到 development Go 后接入：提出需求 → 筛选候选 → 解释理由 → 用户确认 → 发送引荐 → 结果回流。

### M3：活动真实闭环

在活动接口达到 development Go 后接入：活动目标 → 活动方案 → 候选人员 → 用户确认 → 发布邀请 → 报名跟踪 → 活动复盘。

### M4：综合验收

完成真实数据联调、权限与隐私、跨租户隔离、失败恢复、重复执行、成本与并发、安全测试和小范围 UAT。

每阶段仅授权一个最小可测试检查点，平台负责人提交 Handoff 后停止下游修改，等待项目最高负责人给出 Go 或 No-Go。

## 六、硬性技术边界

- 所有产生外部影响的工具调用必须支持显式确认、幂等键、审计链路和可判定的终态。
- 推荐、邀请、消息发送和资料披露必须由服务端权限与租户范围校验；提示词不能作为安全边界。
- 任务恢复不得重复发送邀请、消息或创建业务对象。
- 工具协议必须版本化；兼容变更与破坏性变更分别治理。
- 价格、额度、模型路由、超时和重试次数不得硬编码为业务事实。
- mock 通过仅证明协议可开发，不得标记真实业务闭环或上线验收为 Go。
- 生产数据、真实资金、不可逆操作和生产凭据不在本任务授权范围。

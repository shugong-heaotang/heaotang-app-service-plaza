# 平台交付流优化任务书

- work_id：`AIW-20260713-DELIVERY-FLOW-OPTIMIZATION`
- business owner：项目最高负责人
- blockage owner：平台集成负责人
- verifier：APP 总架构独立验收负责人
- severity：L2 跨单元流程阻滞

## 目标

把“并行过多、Handoff 等待、重复授权、平台负责人单点排队、技术完成但商业结果不清”转换为机器可检查的交付规则：全局最多三个业务主线、每模块最多一个业务主线、Handoff 4 小时响应/24 小时决策、范围内默认自动续跑、一个业务结果对应一个工作项。活动业务主线与商城目录主线先迁入客户价值门禁。

## 边界

只修改治理契约、Schema、验证脚本、测试、状态与 Handoff。不得修改业务代码、部署、生产、真实数据、支付或降低独立验收。现存隔离工作采用 drain mode，不强行中断；新业务主线在降至 WIP 上限前不得激活。

## 验收

1. Policy 与 Schema 可验证。
2. 新增工作项不得省略政策版本或流字段；状态按验证时钟过期、角色未分离和 WIP 超限均失败关闭。
3. 既有未迁移工作不被伪造字段；切换点以前的 work_id 顺序以 SHA-256 固化，切换点后的全部工作项立即受政策约束。
4. 提交或文档本身不能作为完成；integrated 必须同时登记实测且达标的结构化指标、仓库内真实存在的价值事件证据、与登记角色一致的独立 Go 验收、真实 Git 提交及正确祖先关系。
5. 新激活的业务主线必须写明客户、问题、价值事件、指标目标、测量窗口、端到端负责人、商业假设、停止条件和完整旅程范围。
6. 首个跨板块试点为“活动需求 → 俱乐部承接 → 商城目录/无资金履约意向”；仅使用合成数据和失败关闭证据，不授权真实支付、真实触达或生产。
7. `handoff-ready` 必须登记下一责任角色和请求时间；首次响应超过 4 小时或决策超过 24 小时必须由机器门禁报错，并登记升级到项目最高负责人的真实时间。
8. 遗留切换锚点及状态摘要在 Schema 中使用常量锁定；改变遗留状态必须升级合同版本和提供明确迁移记录，不能在同一政策中自行重算哈希通过。

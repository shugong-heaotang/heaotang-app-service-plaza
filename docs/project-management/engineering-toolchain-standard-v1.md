# 和奥堂工程工具链与编码原则 v1

## 原则

语言不是全项目强行统一，而是按职责层统一。前端、后端、验证工具和 Windows 自动化分别使用批准工具链，跨层只通过版本化契约连接。任何接手者先读取 `CONSTRAINTS.md`、适用 ADR、能力注册表和本文件，再修改代码。

## 批准工具链

| 层 | 工具链 | 强制门禁 |
| --- | --- | --- |
| 服务广场前端 | TypeScript strict、React、Vite | 精确依赖版本、锁文件、Vitest、正式构建 |
| 平台后端 | Go、Fiber、database/sql | gofmt、go test、go vet、稳定错误码 |
| 契约与质量验证 | Python 3、JSON Schema | UTF-8、失败非零退出、夹具测试 |
| Windows 自动化 | PowerShell 5.1 兼容 | UTF-8 初始化、BOM/CRLF、外部退出码检查 |

机器基线为 `contracts/foundation/engineering-standards.v1.json`。工具升级是受控依赖变更：先单独升级锁文件，运行全量门禁，记录兼容性结果；不得在业务功能提交中夹带大版本升级。

## 编码边界

- 页面不得直接复制认证、重试、错误解析或幂等实现，只调用共享适配器。
- 后端业务不得相信前端金额；金额使用整数最小货币单位和币种。
- 可变价格、额度、比例、展示规则和生效时间不得硬编码到业务流程。
- 公共能力不得吸收单一业务特例；真实复用后再按能力门禁晋升。
- 发现根因缺陷先修公共层并回归依赖者，不以关闭校验换取编译通过。

## 代码依据追踪

非平凡实现必须能够回答：依赖哪个能力 ID、遵守哪个 ADR/约束、使用哪个契约版本、通过哪些测试。业务模块的 `module-dependencies.v1` 文件承担第一层追踪，Handoff 记录实现和验收证据。

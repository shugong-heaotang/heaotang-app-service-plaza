# 决策 0004：服务广场采用版本化导航接入协议

## 状态

已接受

## 日期

2026-07-10

## 背景

服务广场的长期职责是作为和奥堂 APP 的统一服务导航入口。当前只有生命导航、俱乐部联盟、健康大管家和六个常用服务，未来还会接入内部新板块和外部合作方。

如果每个板块直接向服务广场提供各自的名称、路由、权限说明和返回格式，入口会逐步失去一致性；如果服务广场反过来代理所有板块的业务接口，又会把导航层变成高耦合的业务中台，任何合作方变化都可能影响核心入口。

## 决策

服务广场采用版本化的“导航接入协议”，协议第一版标识为 `service-plaza.v1`。

每个接入板块必须提交符合 JSON Schema 的服务清单。清单统一声明：

- 服务唯一标识、显示名称、摘要、类别和排序；
- 生命周期状态与当前可用性；
- 内部路由、外部 HTTPS 地址或小程序入口；
- 是否需要登录、所需权限范围和交接认证方式；
- 服务能力、提供方标识、隐私等级和返回路径；
- 清单版本及业务接口版本。

服务广场提供统一目录接口，前端以目录接口为入口数据源。服务广场负责发现、展示、排序、权限预检、安全导航和统一返回路径，不代理各板块内部业务操作。

内部板块复用和奥堂会话；外部合作方不得在 URL 中接收 JWT、验证码或个人数据，正式接入时使用 OIDC 授权码模式和 PKCE。未完成板块必须标记为 `planned` 或 `preview`，不能以可用服务展示。

## 考虑过的替代方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 每个板块自行约定入口 | 初期最快 | 命名、权限、状态和返回路径会持续分裂 | 无法支撑规模化对外合作 |
| 服务广场代理所有业务 API | 表面上调用方式统一 | 导航层与所有业务强耦合，责任和隐私边界不清 | 服务广场定位是导航，不是万能业务网关 |
| 只写接入文档，不提供机器可读清单 | 实施成本低 | 无法自动校验、渲染和持续验收 | 标准容易退化为人工约定 |

## 前提

- 服务广场继续作为一级导航页面，而不是承载所有业务流程。
- 板块负责人对本板块业务、数据和合规负责，平台集成负责人对导航协议负责。
- 外部合作方能够提供 HTTPS 入口，并在需要单点登录时支持标准身份协议。
- 如果未来服务数量、租户数量或动态上下线频率显著增加，文件清单可以迁移到审核型服务注册中心，但 `service-plaza.v1` 对外字段保持兼容。

## 影响

### 正面影响

- 新板块可以按同一模板接入，减少逐项沟通和定制代码。
- 服务状态、权限和提供方信息可以自动校验并统一展示。
- 内部业务接口保持独立，避免服务广场成为耦合中心。
- 外部合作不需要共享平台 JWT，降低凭据泄漏风险。

### 已知风险和代价

- 接入方需要维护清单并通过平台校验。
- 第一版采用平台审核后发布，不提供外部自助注册。
- OIDC/PKCE 交接只在协议中锁定，外部单点登录实现需要独立安全验收。

### 后续关注

- 清单签名、合作方证书轮换和域名白名单。
- 服务下线、维护和版本弃用通知机制。
- 动态注册中心启用条件及审核权限。

# 决策 0006：板块扩展前先完成公共基础设施

## 状态

已接受

## 日期

2026-07-10

## 背景

服务广场将持续接入内部板块与外部合作服务。服务目录 `service-plaza.v1` 和页面动作目录 `service-plaza.action.v1` 已经建立统一入口，但认证、接口调用、权限、错误、幂等、可观测性、配置、契约测试和发布回滚如果继续由各板块分别实现，仍会产生重复开发和不兼容改动。

当前各板块的业务功能也处于较大调整期。在业务需求尚未冻结时直接深化板块功能，会把不确定需求写入公共层，随后造成反复修改。

## 决策

在继续扩展板块业务功能前，先完成一层可复用、可验证的公共基础设施。

1. 服务广场两份 v1 契约先冻结，兼容修订按现有治理规则执行。
2. 公共基础设施按 `docs/project-management/service-plaza/common-infrastructure-plan-v1.md` 的 F1 至 F8 顺序建设。
3. 板块在基础设施阶段只允许开发契约适配器、空壳路由、测试夹具和不依赖未决业务需求的组件。
4. 任何公共能力必须有机器可执行契约、自动化测试、运行证据和回滚路径，不能以文档声明代替实现。
5. 发现基础设施问题时暂停受影响的后续工作，先完成根因修复和回归验证，不允许通过关闭门禁、伪造成功或临时分支绕过。
6. F1 至 F6 通过后，各板块可以在稳定入口、认证、错误、幂等和契约测试之上并行开发；F7 至 F8 与板块开发并行完善，但相关发布必须满足对应门禁。

## 考虑过的替代方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 各板块立即全面开发 | 短期页面数量增长快 | 重复实现认证、错误、发布和观测；需求变化导致返工 | 不采用 |
| 一次性建设完整平台后再开发任何板块 | 公共层覆盖最完整 | 周期过长，容易设计超过真实需要 | 不采用 |
| 先做最小公共主链路，再允许并行扩展 | 以真实服务验证基础设施，减少返工 | 需要严格门禁和阶段边界 | 采用 |

## 后果

- 新板块接入从“复制旧代码”转为“提交清单、动作和业务适配器”。
- 公共问题只解决一次，并由契约测试防止回归。
- 板块团队在业务需求冻结后可并行推进，不再等待平台负责人逐项实现。
- 前期会减少可见业务功能增量，但能显著降低后续重复修改和集成风险。

## 重新评估条件

- 服务广场不再承担统一导航与接入治理职责。
- 平台改用独立 API 网关、身份平台或服务目录产品，并覆盖本决策中的能力。
- F1 至 F6 的实际使用证明阶段划分阻碍交付，且有测试证据支持调整。

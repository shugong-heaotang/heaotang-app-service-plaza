# 关键配置采用录入与审核分离

> 状态: 已采纳
> 日期: 2026-07-10
> 决策者: 项目负责人、平台集成负责人

## 背景

价格、容量、费率、功能开关和业务规则会影响用户权益甚至资金。历史接口只校验管理员角色，同一人可以录入并立即生效，误操作和内部滥用都无法由第二人拦截。

## 决策

关键配置采用 maker-checker：录入人只提交 pending 提案；另一名管理员审核；服务端强制 `proposed_by != reviewed_by`；批准后才在同一事务中生成不可变版本，拒绝不生成版本。提交与审核均需幂等键、请求 ID 和原因。旧配置写入口未迁入该流程前保持只读并返回 `CONFIG_APPROVAL_WORKFLOW_REQUIRED`。

## 考虑的替代方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 单管理员直接生效 | 快 | 无职责分离，误改立即影响业务 | 风险不可接受 |
| 同人二次确认 | UI 简单 | 仍不能防止同一主体错误或滥用 | 不是真正审核 |
| 两人录入审核 | 可拦截错误且完整审计 | 配置生效多一步 | 采用 |

## 后果

### 正面影响

- 价格和关键规则不能由单人直接改变。
- 提案、审核、版本和生效时间完整追溯。

### 已知风险和代价

- 紧急变更需要两名可用管理员；后续应制定有时限的紧急审批流程，但不能取消事后复核。

### 需要后续关注的点

- 管理后台增加待审队列和审核通知。
- 功能开关、生命导航运营配置和平台服务费逐项迁入统一提案模型。

## 前提假设

- 平台能够配置至少两名相互独立的管理员；若只有一名管理员，关键参数保持不可变而不是降级为单人审批。
- 审核人能够理解参数影响；若审批只是形式签字，需要补充差异预览和风险提示。

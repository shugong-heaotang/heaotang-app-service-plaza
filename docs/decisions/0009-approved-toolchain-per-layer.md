# 按职责层统一批准工具链与编码原则

> 状态: 已采纳
> 日期: 2026-07-10
> 决策者: 项目负责人、平台集成负责人

## 背景

同一需求由不同人员实现时，如果语言版本、框架、分层边界、错误处理、测试和格式化规则没有统一，代码会产生不可预测差异，接手者也无法知道现有代码依赖什么工程判断。

## 决策

不强求全系统单一语言，而是按职责层固定工具链：服务广场前端使用 TypeScript strict/React/Vite/Vitest；平台后端使用 Go/Fiber/database/sql；契约验证使用 Python 3/JSON Schema；Windows 自动化使用 PowerShell 5.1 兼容 UTF-8 工作流。依赖使用精确版本和锁文件。跨层仅通过版本化契约连接，编码约束进入 `CONSTRAINTS.md` 和自动门禁。

## 考虑的替代方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 全系统只用一种语言 | 表面统一 | 运维、前端、后端和验证职责不同，工具适配性差 | 统一成本高于收益 |
| 开发者自由选择 | 局部效率高 | 维护、招聘、门禁和复用成本持续上升 | 无法形成工程依赖 |
| 按层统一工具链 | 兼顾稳定与适配性 | 需要维护少量跨层契约 | 采用 |

## 后果

### 正面影响

- 接手者能从层级直接判断语言、框架、门禁和代码边界。
- 构建结果可复现，架构差异受 ADR 和契约控制。

### 已知风险和代价

- 工具升级必须独立验证，不能随业务随意升级。
- 团队仍需掌握多种职责层工具，但每层内部保持一致。

### 需要后续关注的点

- 定期检查依赖安全更新，但不得恢复使用 `latest`。
- 新职责层引入新语言前必须写 ADR，并证明现有工具链不适用。

## 前提假设

- 当前 React/Go/Python/PowerShell 分层继续存在；若部署形态根本改变，需要重新评估。
- 锁文件和 CI 门禁持续执行；若无法执行，精确版本本身不足以保证可复现。

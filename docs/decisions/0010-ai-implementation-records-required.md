# AI 辅助实现记录是强制工程依赖

> 状态: 已采纳
> 日期: 2026-07-10
> 决策者: 项目负责人、平台集成负责人

## 背景

AI 可以快速生成大量代码，但未来接手者无法仅从代码判断它依据了哪些需求、公共能力、工具版本和架构判断。若记录只是可选文档，随着人员和模型变化，代码的决策上下文会丢失，后续 AI 也可能按照另一套隐含假设重写同一能力。

## 决策

把实现记录作为 L0 强制依赖。每个非平凡切片必须提交 `implementation-record.v1`，绑定需求来源、能力 ID、契约、ADR、修改区域、验证命令、证据、前提和实现模式。记录通过 Schema 和路径校验后，切片才可从 implemented 升为 verified/deployed。记录缺失或证据路径失效时，不得宣称完成。

## 考虑的替代方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 只保留代码注释 | 距离实现近 | 无法表达跨文件决策、验收和前提 | 追溯范围不足 |
| 只依赖 Git 提交信息 | 成本低 | 提交可能被压缩，无法机器校验完整字段 | 不能成为稳定依赖 |
| 自由格式开发日志 | 表达灵活 | 内容不一致，后续工具无法可靠读取 | 不适合 AI 接续 |
| 机器记录 + ADR + Handoff | 可追溯、可校验、可供后续 AI 使用 | 增加少量记录成本 | 采用 |

## 后果

### 正面影响

- 新人员和新 AI 能从记录恢复实现依据，而不是猜测代码意图。
- 需求、决策、代码、测试和环境证据形成闭环。
- 前提改变时可以定位需要复核的实现切片。

### 已知风险和代价

- 每个重要切片需要同步维护一份结构化记录。
- 记录若不执行路径和状态校验，仍可能与现实漂移。

### 需要后续关注的点

- Handoff 自动引用对应实现记录 ID。
- 定期审计 superseded 决策及其影响的实现记录。

## 前提假设

- 项目文件和测试证据会继续保存在可寻址工作区；若迁移到外部制品系统，需要升级证据 URI 规则。
- 后续 Agent 会读取 `CONSTRAINTS.md` 和实现记录；若运行环境不加载它们，需要在任务入口增加强制检查。
